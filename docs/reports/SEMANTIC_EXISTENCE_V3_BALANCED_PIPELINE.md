# semantic_existence_v3_balanced：负样本是怎样补出来的？

本文根据实际构建器 `build_semantic_existence_v3_balanced.py`、校验器、冻结协议和新增样本记录整理，核对日期为 2026-10-10。这里介绍的是**补充跨视频伪负例的 balanced 版**；其来源是[未补充版](../../data/release/semantic_existence_v3_release/README.md)。两者的实验不能混用，见[版本对照](SEMANTIC_EXISTENCE_V3_VERSION_GUIDE.md)。

## 构造思路

参考 [Moment of Untruth §3.3](https://arxiv.org/html/2502.08544v2#S3.SS3)，**将已有查询与其他视频重新配对，构造域内负例。** 例如，将视频 A 的“一个人喝水”配给另一视频 B，作为 B 的候选负查询。配对只在同组、同一训练/验证/测试划分内进行。

为降低“换了视频，事件却仍然存在”的风险，用 CLIP 比较查询与候选视频已有的事件描述；以最相似的一条描述代表该视频，只从相关性最低的 **50% 视频**中采样。这样可避开已有描述与查询相近的视频。

在此基础上，我们进一步去重、排除语义冲突，将通过筛选的配对记为**无时间段的伪负例**。保留全部原始样本，追加至每个完整划分正负 **1:1**；新增负例未经逐视频核验。

## 1. 先看懂一条新负样本

原始数据里有视频 A，配有一条真实发生的事件描述，例如“一个人用杯子喝水”。balanced 的做法是：**保留这句话，把它配给同一划分里的另一个视频 B；经过筛选后，把“视频 B＋这句话”记作一条伪负例。**

“伪负例”表示这是根据筛选规则假定缺席的事件，没有逐条看视频确认。新的查询没有改写成别的句子，也没有给原视频 A 改标签。

下面是一条真实新增记录，不是虚构示意：

| 字段 | 实际值与含义 |
|---|---|
| 所属划分 | `A1_v3 / test` |
| 借用的查询 | `person drinks out of a cup.`，即“一个人用杯子喝东西” |
| 查询原来来自哪里 | 正例 `test3063`，来源视频 `MZ3I3` |
| 现在配给哪个视频 | `QVD5B`；其已有干净正例描述为“一个人在门厅里拿着一个包” |
| 目标视频的相似度分数 | `0.7135528922` |
| 这段视频在候选中的排名 | 从低到高第 60 名，共 1,301 个候选；允许进入候选池的是前 650 名 |
| 新样本的标签 | `exist_label=0`、`relevant_windows=[]`、`partition=S-` |
| 为什么属于 S− | A1 留出的是物理放置/拿取，“喝东西”不是 A1 的留出动作；S/U 由查询语义决定，不由目标视频内容决定 |
| 核验状态 | `pseudo_absent_unverified`：没有逐视频确认事件缺席 |

这条记录的分数高于 0.5，仍符合规则，因为**筛的是排名较低的一半，不是要求相似度低于 0.5**。目标视频现有标注没写“喝东西”，也不等于已经证明视频中绝无这一事件。完整原始记录见[示例 JSON](semantic_existence_v3_balanced_pipeline_evidence/example_added_negative.json)。

## 2. 为什么要补？补多少？

未补充版保留了通过文本语义审核的原始负例，正例更多。balanced 保留所有原始行，只增加负例，使**每个组的每个完整 Train、Val、Test 都达到正负 1:1**。不增加正例，不移动视频，不重新划分原始样本。

假设某个 split 有 P 条正例、N 条原始负例，新增数量就是 `P − N`。例如 A1 测试集：

| 步骤 | 正例 | 负例 | 总行数 |
|---|---:|---:|---:|
| 原始数据 | 3,453 | 1,158 | 4,611 |
| 新增伪负例 | 0 | 2,295 | 2,295 |
| balanced 数据 | 3,453 | 3,453 | 6,906 |

五组的具体数量如下，括号内是该 split 新增的伪负例数：

| 组 | Train：正 / 负（新增） | Val：正 / 负（新增） | Test：正 / 负（新增） |
|---|---:|---:|---:|
| A1_v3 | 8,801 / 8,801（7,783） | 1,119 / 1,119（724） | 3,453 / 3,453（2,295） |
| A2_v3 | 9,791 / 9,791（8,773） | 1,119 / 1,119（724） | 3,453 / 3,453（2,295） |
| A3_v3 | 9,747 / 9,747（8,729） | 1,119 / 1,119（724） | 3,453 / 3,453（2,295） |
| C1_v3 | 10,042 / 10,042（9,203） | 1,119 / 1,119（724） | 3,453 / 3,453（2,295） |
| C2_v3 | 10,100 / 10,100（9,261） | 1,119 / 1,119（724） | 3,453 / 3,453（2,295） |

合计新增 **58,844 条独立 qid 的伪负例**，其中 S− 57,682 条、U− 1,162 条。五组复用原始视频和查询，不能把累计行数当作互不重叠的视频量或原始查询量。

## 3. 六步生成流程

[![Balanced v3 跨视频伪负例生成、筛选与校验流程](../../assets/semantic_existence_v3/balanced_pipeline.svg)](../../assets/semantic_existence_v3/balanced_pipeline.svg)

保留原始样本，追加跨视频伪负例；1:1 指完整 split，新增标签未逐视频核验。

### 第一步：只在当前组、当前 split 里找查询和视频

每次单独处理一个组的一个 split，例如 `A1_v3/test`。查询来自这个文件中已有的正例，目标视频也来自这个文件；排除查询原来的视频。因此 train 只借 train 的查询并配给 train 视频，val/test 同理。

完全相同的查询文本只保留一个来源代表，取 qid 字典序最小的一条，避免一句在原始标注中重复多次的话获得额外抽样权重。同一句话后续可以配给多个不同视频；同一组、同一 split 中相同的“视频＋规范化查询”只能出现一次。

### 第二步：用已有描述判断哪些视频“看起来不太相关”

筛选阶段不直接用视频画面算相似度。它比较的是：

> 借来的查询 ↔ 目标视频已有的每一条干净正例描述。

CLIP 把两侧的文本各转成一个归一化向量，计算余弦相似度。一个视频可能有多条描述，**取其中最高的相似度作为这个视频的分数**。

以下数值仅为讲解示意，不是新增记录的实际分数：

| 借来的查询 | 目标视频已有描述 | 各描述相似度 | 目标视频最终分数 |
|---|---|---|---:|
| “一个人用杯子喝水” | “一个人在门厅拿着包”；“一个人在走动” | 0.62；0.57 | 0.62 |
| “一个人用杯子喝水” | “一个人坐着”；“一个人在喝东西” | 0.55；0.91 | 0.91 |

为什么取最高值？因为只要目标视频的一条已知描述很像这句查询，就应提高警惕；平均值可能把这条明显相关的描述稀释掉。这个分数只是候选筛选依据，**不是事件存在概率**。

参考描述来自源 `master/positive_clean.jsonl` 中该视频的全部干净正例，不只是当前 split 文件内保留下来的查询。对于训练视频，因语义留出而没有放进训练集的正例描述也会参与这个分数和后续冲突检查，目的是减少假负例；这些 held-out 查询不作为训练样本加入。这个数据构造时使用完整标注的边界应明确报告。

### 第三步：对每条查询单独排名，保留最低一半

先排除查询原视频，再把其余候选视频按分数从低到高排序。如果有 N 个候选，只保留前 `floor(N/2)` 个。完全同分时按视频 ID 字典序排序，保证结果可重现。

例如有 10 个候选视频，就保留分数最低的 5 个；有 1,301 个，就保留前 650 个。不同查询各排各的名，没有所有查询共用的相似度阈值。

这也不表示每条查询最后都生成一半视频数量的负例。最低一半只是**候选池**；后续还要过滤，并且只抽取补齐数量所需的配对。

### 第四步：从候选池排除重复或有标注冲突的配对

排名靠前仍不够，还要逐个检查目标视频已有正例的完整查询与事件：

| 检查 | 代码如何处理 | 用意 |
|---|---|---|
| 重复配对 | 已有原始行或本轮新增行中出现相同目标视频＋规范化查询，就跳过 | 避免重复样本 |
| 完全相同的正例查询 | 目标视频已有同一句规范化查询，就跳过 | 避免把已标注存在的事件写成缺席 |
| 相同/别名动作与兼容对象 | 动作相同或别名归一后相同，且对象相同、包含、通用或未指定，或角色不同而无法安全区分，就跳过 | 保守排除潜在语义重合 |
| 指定相反动作与兼容对象 | 如 open/close、take/place 等指定动作对，满足对象/锚点兼容或不明确条件时跳过 | 额外降低歧义；不表示两个相反动作不能在同一视频中先后发生 |

事件检查跳过 purpose、intended、negated 等非已断言发生的事件。sofa/couch、cupboard/cabinet 等对象别名，以及若干动作别名会先归一化。

**顺序是先截取最低一半，再执行这些过滤。** 被过滤掉的候选不会用排名后一半的视频来补位；如果剩余候选无法满足配额，构建器报错，不放宽排名规则。

### 第五步：按名额抽取，而不是把所有候选都加入

抽样以 seed 3407 为起点，为每个组/split 派生独立随机种子。每一轮打乱查询的访问顺序；每条查询的最低半区视频列表也先打乱，再依次尝试。每次访问一条查询，最多接收一个合格目标视频；下一轮再轮到它，直到补够数量。

这让查询轮流参与，但不保证每句产生完全相同数量的负例：有些查询候选不足，有些所属 S/U 名额已经补满，会被跳过。

新样本的 S/U 按借来查询的完整事件语义重新判断，沿用 v3 原来的 held-out 规则。训练来源只有 S+，所以新增训练负例只能是 S−。验证/测试按原来 S+ 与 U+ 的比例分配**本次新增**的 S−/U− 名额，用最大余数法处理整数舍入。

以 A1 test 为例：2,857 个 S+、596 个 U+，需要新增 2,295 条负例。分配结果是新增 S− 1,899 条、U− 396 条；加上原来的 S− 983 条、U− 175 条，得到最终 S− 2,882 条、U− 571 条。

### 第六步：写一条可追溯的新记录

| 信息 | 从哪里来 / 怎样生成 |
|---|---|
| 查询、完整事件与语义图 | 复制来源正例；不改写查询 |
| vid、duration | 使用目标视频，不是来源视频 |
| qid | 根据版本、组、split、目标视频和来源 qid 生成稳定哈希，避免与原始 qid 混淆 |
| exist_label、relevant_windows | 设为 `0` 和 `[]` |
| partition | 按查询语义设为 S− 或 U− |
| source_qid、source_vid、source_windows | 保存来源和原正例时间窗，供追溯；原时间窗不是新样本 GT |
| clip_filter | 保存分数、升序排名、候选数、截断分数及目标参考描述数 |
| 核验标记 | 明确记录“仅 CLIP 排名与标注过滤、没有视频核验” |

原始行作为完整字节前缀保留，新增行追加在末尾。新增负例单独写入 `master/negative_added.jsonl` 和 `provenance/<group>/<split>_added.jsonl`；`master/negative_clean.jsonl` 仍是原来审核保留的负例池。实际训练与评估应读完整 `splits/`，否则读不到新增样本。

## 4. “balanced”不表示哪些事情？

**只保证每个完整 split 的正负总数相同，不保证 Seen 和 Unseen 子集各自 1:1。** 例如 C1 test 原来已经有 U+ 142 条、U− 264 条；保留原始样本且只加负例，无法让这个子集变成 1:1。补充后仍是 U+ 142、U− 358。

它也不表示各组增强后的训练负例完全相同。原来的共享审核负例池保留，但每组补充量和语义留出条件不同，新增负例按组生成，完整训练池随之不同。

原始 matched-U 配对文件保持不变。新负例是跨视频配对，不能称为同一视频里从同源事件构造的匹配反事实对，也不自动进入原始 matched-U 测试。

## 5. 校验到底证明了什么？

已保存的校验结果为 **PASS**：15 个组/split 通过检查，58,844 条新增配对全部重算了 CLIP 分数和排名。它检查了：

- 原始文件校验和、原始行字节前缀、标签和视频归属保持一致。
- 完整 split 正负 1:1、视频/qid 跨 split 隔离、训练只有 S+/S−。
- 来源确实是同组同 split 的正例，目标是另一视频，查询和语义未改动，时长来自目标视频。
- 空窗口、伪负例标记、去重、标注冲突规则及 S/U 新增配额正确。
- 全部新增配对的分数、排名、候选数量、最低半区截断值与冻结文本向量重算一致。
- master、provenance、统计和 `val_seen.jsonl` 相互对应。

**PASS 证明构建结果符合这套规则，不证明每条负例在视频中真的缺席。** 校验复用冻结向量，没有重新编码所有文本，也没有逐视频观看。视频已有标注不完整时，仍可能产生假负例。

## 6. 技术细节与追溯入口

文本编码采用 OpenAI CLIP ViT-B/32 的 EOT 句向量，经 `text_projection` 投影、转 float32 并 L2 归一化。15,034 条源正例按完整查询去重后，共编码 9,017 条不同文本。使用 CLIP BPE 分词、SOT/EOT 与 77-token 上下文；超长报错，不静默截断。计算向量点积时关闭 CUDA TF32。

分数公式为 `score(q, v) = max cosine(CLIP(q), CLIP(t))`，其中 t 遍历目标视频 v 的全部干净正例描述。构建记录注明参考 Moment of Untruth 的 in-domain negative 思路；上述六步描述以本项目实际实现为准，项目增加的标注过滤、配额和留出约束不能一概视为论文原方法。

数据、构建器、校验器和完整 provenance 当前保留在本地工作仓库，数据目录为 `data/release/semantic_existence_v3_balanced/`；本分支发布的是说明及轻量证据。对应函数为：`pseudo_scores()` 计算文本分数，`event_conflict()` 排除标注冲突，`quotas()` 分配新增 S/U 名额，`add_negatives()` 排名/抽样/生成，校验器 `validate()` 重算和验收。

用于筛选的 512 维句子向量与训练所需的文本特征不是一个缓存用途：后续训练可在核对查询文本一致后复用来源正例的文本特征，视频特征必须使用目标视频的特征。

## 7. 实验结果应怎样解释？

完整数据平衡不等于已验证事件缺席，也不意味着模型必然更好。Rej-F1 和 G-mIoU 会随正负样本比例变化；balanced 与未补充版的训练、验证和完整测试集都不同，直接相减不能归因为“补负例的收益”。如果要研究新增训练负例的作用，应冻结同一个测试集，再比较同 backbone 的两套训练结果，并使用各自合法 Seen validation 选择模型和阈值。

每套实验仍须报告 AUROC、Rej-F1、G-mIoU@1 的 Seen/Unseen、Gap 和视频级 bootstrap CI，同时给出 RR、S+/U+ FRR 及子集正负数。数据构建文档不承担动态实验进度；各版本结果和快照时间以[版本对照中的结果入口](SEMANTIC_EXISTENCE_V3_VERSION_GUIDE.md)为准。
