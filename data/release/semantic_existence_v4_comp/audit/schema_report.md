# v3 Release Audit: Data and Schema

## Scope and inputs

This audit reads `data/release/semantic_existence_v3_release/` and the repository's existing construction/validation scripts. It does not modify v3. The cleaned master annotation tables contain 15,034 positive rows and 2,869 negative rows over 6,507 distinct videos. The release says its clean sets are the audited, usable rows; it does not publish the full original source split manifest or per-qid review records.

The master rows retain positive `relevant_windows` and negative empty windows. All 15,034 positive rows have at least one event in `events`; 1,824 positive queries have multiple event records, and the event-list length distribution is 13,475 one-event, 1,495 two-event, 62 three-event, and 2 four-event queries. Negatives also retain event lists (3,138 events across 2,869 queries), including multi-event examples. The full event list is the appropriate basis for leakage checks. `semantic_graph` is explicitly marked as a primary-event projection, so checking only that object loses embedded/coordinated events.

## Video split reconstruction

The master rows have an explicit `split` field. Mapping `vid -> split` across both master files yields 6,507 assignments: 4,707 train videos, 498 validation videos, and 1,302 test videos. There are no conflicting assignments or rows without `split` in these cleaned tables. Reconstructing assignments from every row in each of `A1_v3`, `A2_v3`, `A3_v3`, `C1_v3`, and `C2_v3` yields the same mapping: zero cross-group conflicts and zero conflicts with the master `split` field. Train/validation/test video sets are disjoint.

The v3 `input_inventory.json` separately records 6,670 source video assignments, 163 more than the 6,507 videos represented by the clean masters. No `video_splits.jsonl` or full source assignment file is present in the release. Thus the released v3 split assignment is reconstructible and consistent for every video used in the clean release, but not for those additional 163 source videos. A v4 builder restricted to v3 clean annotations can faithfully preserve the 6,507-video allocation; it cannot claim to reconstruct the absent source assignment rows.

## Semantic representation and coverage

The full `events` list is the strongest available semantic representation. Event records usually include `action_family`, `anchor_role`, and `anchor_object`, and can add role/state/aspect attributes such as `agent`, `source`, `goal`, `location`, `support_surface`, `instrument`, `manner`, `aspect`, `state_change`, `assertion`, `temporal_relation`, `path`, `target`, `contents`, and `purpose`. The schema is permissive rather than a fixed typed graph: many useful attributes are sparse, and additional event-specific keys occur in the long tail. Do not fill absent roles by inference.

Across positive master rows there are 16,659 event records. Every event has an `action_family`; 16,636 have an `anchor_role` and 16,461 have an `anchor_object`. Thus 23 positive event records lack the anchor role and 198 lack an anchor object. The most frequent explicit `anchor_role` counts are `theme` 12,463, `agent` 2,900, `support_surface` 790, `target` 135, `location` 129, `goal` 107, `source` 63, and `instrument` 33. These counts are not counts of all `goal`/`source` attributes: those also appear as separate event attributes on other anchor roles. `patient` is not a prevalent canonical role in this release; the annotation convention primarily uses `theme`.

Composition profiling is strongest for action–theme/object and action–support-surface relations. Goal and source relations are present but substantially thinner; instrument is sparse. `agent` is often represented as an anchor role for intransitive actions, while person/agent information may also appear in an `agent` value. That distinction needs to be preserved rather than collapsing agent and patient roles. Event action vocabulary is broad and long-tailed: the positive inventory has 196 distinct action-family values among resolved event records, with many singleton or very low-support labels. Exact string counts do not establish ontology equivalence.

The v3 ontology licenses a small, explicit set of aliases/action-sense distinctions, including sofa/couch, contextual cabinet/closet overlap, cabinet-entry normalization for opening/closing a cabinet door, and separate physical-take, drink, photograph, run, walk, and physical-place senses. It specifically warns to preserve source/destination direction and distinguishes put-into from take-out. These rules are the initial authority; the v4 composition key must include role and normalized filler and should leave unresolved or ambiguous events out of eligible counts.

## Provenance and limitations

`positive_clean.jsonl` rows are original positive queries with their original windows and carry `source_qid`, source `split`, event lists, and full-audit disposition. The clean positive master has 15,034 qids. `negative_clean.jsonl` has 2,869 qids and distinguishes negative construction type, source positive, semantic review method, and `verification_status`. The current v3 ontology's review protocol uses text/event comparison and a short-video construction assumption; `release_info.json` says video review was not performed. The full-audit release has no per-qid review records. These inherited negatives should retain their exact provenance and must not be described as visually verified.

Release-wide inventory counts list 16,124 unique source positive qids and 9,956 parser/event records before clean selection, with 1,048 unresolved positive qids; only the clean subset is included in the published positive master. The audit excluded/quarantined rows are not in the clean release. The clean annotations therefore offer excellent structured coverage for many core events but do not provide complete source data or raw video evidence.

## Existing code reuse findings

- `scripts/build_semantic_existence.py` contains reusable JSONL I/O, deterministic hashing, and some source/video conflict utilities. Its local `canonicalize()` is a spaCy first-content-verb/one-object parser; it is not adequate as the v4 event extractor and should not replace v3's full event list or infer role direction.
- `scripts/profile_semantic_split_candidates.py` has useful profiling patterns for counts, videos, and vocabulary. It parses original captions rather than consuming v3's full structured event annotations, so its inferred action/object pairs are not an authoritative v4 source.
- `scripts/validate_release.py` is a legacy v1 package validator with a single `semantic_graph` action/object view and requires a verified-negative status. It is not a v3 full-event leakage validator and should not be used unmodified as the v4 semantic gate.
- `scripts/package_semantic_multisplit.py` demonstrates deterministic JSONL serialization, frozen-selection hash checks, matched-pair checks, and SHA-256 packaging. Its v2 package assumptions include reviewed negatives and an external video archive; adapt only the generic integrity/hash patterns.
- `scripts/review_semantic_multisplit.py` supports export/import of candidate review queues and exact prior-release negative reuse. Its approved path can turn a global batch attestation into a video-review status, which is not suitable for v4 candidates without an equivalent genuine visual review. The export/import provenance mechanics can be adapted while keeping candidates quarantined/unverified.

The v3 `split_specs.json` records five existing groups (A1/A2/A3 action-family holdouts; C1/C2 action–object holdouts) and says to use the shared video split assignment. The packaged split rows provide the required recoverable assignment for all 6,507 clean-release videos. For compositional v4, `events` plus `ontology/rules.json` are the authoritative starting point; `semantic_graph` should only be used as a convenience projection, never as a complete leakage check.
